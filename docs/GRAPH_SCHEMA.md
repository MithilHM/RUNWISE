# RUNWISE FalkorDB Graph Schema and Lineage Reference

This document describes the graph database architecture, node schemas, relationship semantics, key Cypher queries, and correction-impact workflows implemented for **RUNWISE**.

---

## 1. Graph Model Overview

RUNWISE uses **FalkorDB** to model the entities and directed dependencies produced during machine learning experimentation. Rather than storing flat run logs, RUNWISE persists an explicit lineage and provenance graph that answers:

1. Under what conditions (datasets, versions, configurations, hardware) was an experiment conducted?
2. How do experiments relate to each other (parent lineages, comparative baselines, distilled models)?
3. What metrics and scientific claims did each experiment produce?
4. When underlying evidence or data is corrected, which downstream experiments and conclusions become suspect?

## 2. Node Labels and Properties

| Label | Key Properties | Purpose |
|---|---|---|
| `Project` | `id` (indexed), `name`, `description`, `created_at` | Top-level project boundary containing experiment runs. |
| `Experiment` | `id` (indexed), `project_id` (indexed), `name`, `model_family`, `status`, `quality_status`, `duration_seconds`, `compute_cost_gpu_hours`, `random_seed`, `created_at` | A single experimental training or evaluation execution. |
| `Configuration` | `id` (indexed), `canonical_json`, `config_hash` (indexed), `created_at` | Normalized, deterministic JSON configuration of hyperparameters and model options. |
| `Dataset` | `id` (indexed), `name`, `description` | High-level dataset entity (e.g., `tabular_fraud`, `cifar10`). |
| `DatasetVersion` | `id` (indexed), `dataset_id` (indexed), `version`, `quality_status`, `created_at` | Specific snapshot or version of a dataset used in training/eval. |
| `Metric` | `id` (indexed), `experiment_id` (indexed), `name`, `value`, `direction`, `evaluation_split`, `evaluation_protocol` | Empirical result observed during an experiment run. |
| `Hypothesis` | `id` (indexed), `text`, `status`, `created_at` | Scientific hypothesis tested by one or more experiments. |
| `Claim` | `id` (indexed), `text`, `status`, `confidence`, `created_at`, `reviewed_at` | Conclusion or scientific claim derived from experiment results. |
| `Evidence` | `id` (indexed), `source_type`, `source_reference`, `description`, `created_at` | Raw documentation or artifact supporting a claim. |
| `Correction` | `id` (indexed), `project_id`, `source_id`, `source_type`, `description`, `evidence_reference`, `status`, `created_at`, `created_by`, `impact_summary` | Audit record documenting an evidence or data invalidation event. The project and source are stored on the node so the audit history can be read back without replaying every relationship. |
| `ReviewItem` | `id` (indexed), `project_id`, `reason`, `status`, `experiment_id`, `correction_id`, `created_at`, `resolved_at`, `resolved_by`, `resolution_notes` | Actionable queue item flagged for researcher review during revalidation. `status` is one of `open`, `resolved`, `dismissed`. |
| `Recommendation` | `id` (indexed), `project_id`, `objective`, `hypothesis`, `status`, `score`, `estimated_gpu_hours`, `evidence_status`, `candidate_kind`, `created_at`, `canonical_json`, `decided_by`, `decision_note`, `decided_at` | Advisory next-experiment proposal generated by copilot. `canonical_json` holds the full payload so a stored proposal round-trips exactly; the other properties are promoted because the UI filters and sorts on them. |
| `Researcher` | `id` (indexed), `name` | Human researcher identity associated with reviews or runs. |
| `ChatSession` | `id` (indexed), `project_id` (indexed), `title`, `created_at`, `updated_at` | Persistent conversation session in FalkorDB (Track 02). |
| `ChatMessage` | `id` (indexed), `session_id` (indexed), `role`, `content`, `mode`, `llm_used`, `timestamp` | Historical chat interaction preserved across sessions (Track 02). |
| `Agent` | `name` (indexed) | Autonomous agent identity participating in coordination handoffs (Track 02). |
| `FailureReason` | `id`, `reason`, `category`, `created_at` | Failure cause node in learned failure subgraphs (Track 01/02). |

## 3. Relationship Types and Semantics

```text
(Project)-[:CONTAINS]->(Experiment)
(Project)-[:CONTAINS_SESSION]->(ChatSession)
(ChatSession)-[:HAS_MESSAGE]->(ChatMessage)
(ChatMessage)-[:CITES_EXPERIMENT]->(Experiment)
(Agent)-[:HANDED_OFF]->(Agent)
(Dataset)-[:SIMILAR_REGIME]->(Dataset)
(Experiment)-[:EVALUATED_ON]->(Dataset)
(Experiment)-[:FAILED_UNDER]->(FailureReason)
(Experiment)-[:DERIVED_FROM]->(Hypothesis)
(Experiment)-[:USES_CONFIG]->(Configuration)
(Experiment)-[:USES_DATASET_VERSION]->(DatasetVersion)
(DatasetVersion)-[:VERSION_OF]->(Dataset)
(Experiment)-[:PRODUCES_METRIC]->(Metric)
(Experiment)-[:TESTS]->(Hypothesis)
(Experiment)-[:BASED_ON]->(Claim)
(Claim)-[:SUPPORTED_BY]->(Evidence)
(Claim)-[:CONTRADICTS]->(Claim)
(Claim)-[:SUPERSEDES]->(Claim)
(Experiment)-[:PARENT_OF]->(Experiment)
(Experiment)-[:COMPARED_WITH]->(Experiment)
(Correction)-[:CHALLENGES]->(Evidence)
(Correction)-[:AFFECTS]->(DatasetVersion | Experiment)
(Recommendation)-[:SUPPORTED_BY]->(Experiment)
(Recommendation)-[:PROPOSES]->(Experiment)
(ReviewItem)-[:CONCERNS]->(Experiment)
(Experiment)-[:REVIEWED_BY]->(Researcher)
```

Two relationships were added after the table above was first written, and both exist
because the PRD's audit requirements are otherwise unreachable:

```text
(ReviewItem)-[:RAISED_BY]->(Correction)      # which correction opened this queue item
(Project)-[:HAS_RECOMMENDATION]->(Recommendation)   # a proposal's owning project
```

A `ReviewItem` is linked to its correction by a real relationship rather than by an
identifier prefix, so "show me every review item this correction caused" is a graph
traversal. `(Recommendation)-[:PROPOSES]->(Experiment)` is intentionally unused: a
proposal is not a run, and inventing an experiment node to point at would put a
fabricated result into the graph.

## 3.1 Uniqueness

The FalkorDB build this project targets does not support uniqueness constraints
(`CREATE CONSTRAINT ... IS UNIQUE` is rejected). Node identity is therefore enforced
by `MERGE (n:Label {id: $id})` on every write, which is idempotent for an unchanged
record. `initialize_schema` probes for constraint support once per process and
reports the result, so an upgrade that gains the feature is visible rather than
assumed.

## 3.2 Cypher the engine accepts, and what it does not

Verified against FalkorDB 4.22 by `python scripts/probe_cypher_support.py`. Re-run it
after a server upgrade; every constraint below is a deliberate consequence of a
measured limitation, not a style choice.

| Construct | Supported | How the repository works around it |
|---|---|---|
| Pattern predicate in `WHERE`, e.g. `(e)-[:USES_DATASET_VERSION]->(:DatasetVersion {dataset_id: $id})` | yes | Used for the dataset-scope filter. |
| Conditional aggregate as a filter, `sum(CASE WHEN ... END) AS hits` then `WHERE hits > 0` | yes | Used for the metric and evaluation-split filters, so filtering stays server-side and case-insensitive. |
| `any(x IN collect(...) WHERE ...)` | yes | Used to derive a legacy correction's project scope. |
| Multi-type relationship, `[:AFFECTS|CHALLENGES]` | yes | Used for correction targets. |
| `UNWIND relationships(path)` | yes | Used for lineage edge extraction. |
| `coalesce(a, b)` in `ORDER BY` | yes | Orders by the source timestamp, falling back to the import time. |
| `OPTIONAL MATCH` then `DELETE` | yes | Used to replace a run's `USES_CONFIG` / `USES_DATASET_VERSION` edge. A plain `MATCH` here would produce no rows on a first import and silently skip the rest of the query. |
| `EXISTS { MATCH ... }` subquery | **no** | Replaced by a pattern predicate or a conditional aggregate. |
| `exists((e)-[:REL]->())` | **no** | Replaced by a pattern predicate. |
| Pattern comprehension `size([(e)-[:REL]->(x) WHERE ... \| x])` | **no** | Replaced by a conditional aggregate. |
| `WITH ... WHERE ... ORDER BY` in one clause | **no** | An intermediate `WITH` is inserted between the filtering clause and `ORDER BY`. |
| `CREATE CONSTRAINT ... IS UNIQUE` | **no** | Identity rests on `MERGE`; see 3.1. |

## 4. Key Cypher Query Patterns

### A. Experiment Retrieval with Metrics and Provenance
```cypher
MATCH (e:Experiment {id: $exp_id})
OPTIONAL MATCH (e)-[:USES_CONFIG]->(c:Configuration)
OPTIONAL MATCH (e)-[:USES_DATASET_VERSION]->(dv:DatasetVersion)-[:VERSION_OF]->(d:Dataset)
OPTIONAL MATCH (e)-[:PRODUCES_METRIC]->(m:Metric)
OPTIONAL MATCH (parent:Experiment)-[:PARENT_OF]->(e)
OPTIONAL MATCH (e)-[:PARENT_OF]->(child:Experiment)
OPTIONAL MATCH (e)-[:BASED_ON]->(claim:Claim)
RETURN properties(e), c.canonical_json, d.name, dv.version,
       collect(DISTINCT properties(m)),
       collect(DISTINCT parent.id),
       collect(DISTINCT child.id),
       collect(DISTINCT properties(claim))
```

### B. Bounded Lineage Traversal (Ancestors and Descendants)
```cypher
// Downstream lineage: root -> children -> grandchildren
MATCH path = (root:Experiment {id: $exp_id})-[:PARENT_OF*1..5]->(child:Experiment)
RETURN [n in nodes(path) | properties(n)] AS path_nodes,
       [r in relationships(path) | [startNode(r).id, endNode(r).id]] AS path_edges
```

### C. Direct Dataset Dependency Lookup
```cypher
MATCH (e:Experiment)-[:USES_DATASET_VERSION]->(dv:DatasetVersion {id: $dataset_version_id})
OPTIONAL MATCH (e)-[:PRODUCES_METRIC]->(m:Metric)
RETURN e.id AS experiment_id, e.name AS experiment_name, e.status AS status,
       collect({name: m.name, value: m.value, split: m.evaluation_split}) AS metrics
```

### D. Correction Impact Traversal and Path Extraction
```cypher
// Directly affected experiments
MATCH (e:Experiment)-[:USES_DATASET_VERSION]->(dv:DatasetVersion {id: $source_id})
RETURN e.id

// Transitive downstream experiments via parent-child lineage
MATCH path = (parent:Experiment {id: $direct_id})-[:PARENT_OF*1..5]->(downstream:Experiment)
RETURN downstream.id,
       [n in nodes(path) | n.id] AS node_ids,
       [r in relationships(path) | type(r)] AS rel_types

// Claims dependent on affected experiments
MATCH path = (e:Experiment {id: $exp_id})-[:BASED_ON]->(cl:Claim)
RETURN cl.id, [n in nodes(path) | n.id] AS node_ids, [r in relationships(path) | type(r)] AS rel_types
```

## 5. Correction and Impact Semantics

### Conservative Revalidation Principle
In accordance with PRD Section 5 (FR-6):
- **Graph reachability establishes dependency, not scientific invalidity.**
- When a dataset version or evidence claim is marked unreliable:
  - Source node is marked `unreliable` or `leakage_detected`.
  - Dependent experiments are set to `quality_status = "needs_review"`.
  - Actionable `ReviewItem` entries are created in the revalidation queue.
  - Historical records and produced metrics are **preserved** (never destructively deleted).
  - Unaffected experiments in the same project remain marked `valid` and available for baseline comparisons.
